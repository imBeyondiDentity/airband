# Airband — исследование №2: как поднять браузерную версию до уровня Python

Три части: что показал анализ кода, с чем сравнивала, что предлагаю
сделать и в каком порядке. В конце — таблица, что из найденного можно
брать кодом, а что только идеей.

---

## Коротко

1. **В браузерной версии найден реальный баг измерения пика.** Функция
   `truePeakDb` по факту меряет сэмпловый пик, а не true peak. На худшем
   случае ошибается на 3 дБ. Это значит, что при потолке −1 dBTP реальные
   межсэмпловые пики могут доходить до +2 dBTP — после конвертации
   в AAC/MP3 на стримингах это клиппинг. Чинится первым делом.
2. **Главный слышимый разрыв с Python — слежение за огибающей.** В браузере
   новый верх подмешивается ровным слоем с постоянным уровнем, в Python
   он следует за музыкой кадр за кадром. Это переносится, весь нужный
   инструментарий (FFT) в браузерном коде уже есть.
3. **Самая важная идея из исследования касается обеих версий.** Экситер
   Airband питается полосой примерно 6.7–15 кГц — а именно там живут
   фирменные артефакты Suno («шиммер», металлическое шипение). Сейчас
   Airband берёт этот мусор и размножает его гармониками вверх, в полосу
   «воздуха». Нужна стадия очистки **до** экситера: сначала чистим,
   потом достраиваем.

## 1. Анализ кода: браузер против Python

### Баг: «true peak» на самом деле сэмпловый пик

Браузерная функция ищет пики между сэмплами линейной интерполяцией. Но
точка на прямой между двумя сэмплами по определению не может быть выше
большего из них — линейная интерполяция никогда не найдёт межсэмпловый
пик. Проверила численно на классическом худшем случае (синус на четверти
частоты дискретизации со сдвигом фазы 45°):

| Что меряем | Результат |
|---|---|
| Сэмпловый пик | −3.01 dBFS |
| «True peak» браузерной версии | −3.01 dBFS |
| Реальный пик сигнала | 0.00 dBFS |

Python-версия этим не страдает: там честная полифазная передискретизация
через scipy.

**Исправление:** реализовать измерение true peak по стандарту ITU-R
BS.1770-4 (приложение 2) — 4-кратная передискретизация полифазным
FIR-фильтром. Коэффициенты фильтра опубликованы в самом стандарте.
Как эталон для сверки — libebur128 (MIT), у неё есть свой FIR-ресемплер
для true peak и тесты на соответствие стандарту. Плюс лимитер должен
опираться на тот же честный замер, а не на сэмпловый пик.

### Таблица разрыва

| Что | Python | Браузер | Насколько важно |
|---|---|---|---|
| True peak | честный, полифазный | **фактически сэмпловый** | критично |
| Уровень нового верха | следит за огибающей | постоянный слой | главное на слух |
| Фильтры полос экситера | FIR, линейная фаза | IIR (биквады) | средне |
| Оверсэмплинг насыщения | свой полифазный 4× | `WaveShaper '4x'`, качество фильтра зависит от браузера | средне |
| Подгонка под референс | есть | нет | средне |
| Альбомный режим | есть | нет (только пакет) | средне |
| Где считается | — | в главном потоке, интерфейс замирает на длинных треках | удобство |
| Ресемплинг при чтении | scipy / ffmpeg | `decodeAudioData`, качество зависит от браузера | низко–средне |
| Лимитер с hold | есть | есть | паритет ✓ |
| Авто-параметры | есть | есть | паритет ✓ |
| Итеративная нормализация | есть | есть | паритет ✓ |

Замечание про IIR в экситере: для самого экситера это не катастрофа —
сухой сигнал живёт ниже среза, новый материал выше, они почти не
пересекаются, и фазовый сдвиг биквадов там мало что портит. Поэтому
переход на FIR — не первоочередной.

## 2. С чем сравнивала

| Проект | Что делает | Лицензия | Чем полезен Airband |
|---|---|---|---|
| **Shimmer** (henricksmedia) | чистка артефактов Suno + мастеринг, 19 пресетов, стемы | AGPL-3.0 | только идеи — код брать нельзя |
| **deshimmer** (TheApeMachine) | подавление «шиммера» Suno в 5–7 кГц | MIT | можно брать код с указанием авторства |
| **ai-mastering** (abrahamahn) | мастеринг под Suno: де-харш, стерео, теплота, несколько кандидатов с оценкой | не проверена | идеи |
| **Matchering** | мастеринг по референсу | GPLv3 | уже взята идея hold-лимитера |
| **libebur128** | громкость и true peak по EBU R128 | MIT | эталон для честного true peak |
| **Apollo** (Tsinghua / Tencent) | нейросеть, восстанавливает MP3-сжатую музыку | CC BY-SA 4.0 | опциональный модуль для Python |
| **AudioSR** | нейросетевой апскейл любого аудио до 48 кГц | MIT | опционально для Python, тяжёлый |

### Что важного у конкурентов, чего нет в Airband

**Shimmer** сформулировал главную мысль, которую Airband пока нарушает:
обычный мастеринг принимает шум генерации за часть музыки и делает его
громче — поэтому сначала чистка, потом мастеринг. У Airband ситуация даже
острее: экситер не просто усиливает шиммер, он строит из него новые
гармоники.

Другие их архитектурные решения, которые стоит взять как идеи:

- **Низ не трогается вообще.** Линейно-фазовый кроссовер на 4.5 кГц:
  всё ниже идёт мимо чистки и возвращается нетронутым.
- **Центр микса защищён.** Выше кроссовера сигнал делится на mid/side;
  центр (вокал, рабочий) чистится мягко, примерно на 20% силы, а стороны —
  в полную силу, потому что большая часть шиммера живёт в сторонах.
- **Защита транзиентов.** Отдельный гейт оберегает атаку ударных
  примерно 70 мс, чтобы барабаны не теряли щелчок.
- **Перед лимитером — мягкий клиппер.**
- **Разный потолок под формат:** −1.0 dBTP для lossless, −1.5 dBTP для
  lossy (MP3/AAC).
- **Третий режим прослушки — «Удалённое».** Кроме «до/после» можно
  включить только то, что инструмент вырезал: если там слышен вокал или
  рабочий — режет слишком сильно. Для Airband аналог — прослушать
  отдельно только досинтезированный верх.

**deshimmer** локализует артефакты точнее: узкополосные мерцающие
«птички» в зоне 5.1–7.2 кГц (по умолчанию), подавляет их мягким
коленом, а не жёстким гейтом, и отличает узкие артефакты от
широкополосного полезного материала по плотности спектра. Лицензия MIT —
алгоритм можно переносить в Airband напрямую, с указанием авторства.

**Apollo** — другой класс решения: вместо досинтеза гармоник нейросеть
восстанавливает то, что съел MP3-кодек. Обучена ровно на этой задаче —
на MP3 с битрейтами от 24 до 128 kbps. Но есть две оговорки:
- лицензия CC BY-SA 4.0 (ShareAlike) несовместима с тем, чтобы зашить
  её в MIT-код Airband — только как отдельный опциональный модуль со
  своей лицензией;
- обучена на датасетах MUSDB18-HQ и MoisesDB — у таких датасетов бывают
  ограничения на коммерческое использование, и их стоит проверить
  отдельно, прежде чем выпускать коммерческие треки через эту модель.

**AudioSR** — код под MIT, но это диффузионная модель: нужна видеокарта,
работает медленно. И у неё у самой отмечено, что результат сильно
зависит от характера среза на входе — для Suno это стоит проверить на
реальных треках, а не предполагать.

## 3. Что предлагаю — по приоритетам

### P0 — исправить и догнать Python (браузер)

**1. Честный true peak.** По ITU-R BS.1770-4: 4× полифазный FIR,
коэффициенты из стандарта, сверка с libebur128. Лимитер переводится на
этот же замер. Плюс самотест на тот самый худший случай (синус fs/4,
сдвиг 45°) — он должен показывать 0.00 dBTP, а не −3.01.

**2. Слежение за огибающей.** Перенести из Python: STFT исходника и
синтезированной полосы, наклон спектра по двум полосам под срезом,
экстраполяция выше среза, кадровый гейн со сглаживанием ~25 мс. FFT в
браузерном коде уже есть.

**3. Обработка в Web Worker.** Вынести тяжёлый расчёт из главного
потока: интерфейс перестанет замирать, а заодно появится место для
своего полифазного оверсэмплинга вместо `WaveShaper`.

### P1 — новые модули и фильтры (обе версии)

**4. Де-шиммер перед экситером.** Новая стадия в начале цепочки:
детектор узкополосных мерцающих пиков в 5–14 кГц с мягким коленом,
работает в основном по боковому каналу, центр — бережно, низ ниже
~4.5 кГц не трогает вовсе. Алгоритмическая основа — deshimmer (MIT),
архитектурные идеи — Shimmer. Это единственное изменение, которое
меняет сам смысл обработки, а не только её качество.

**5. Защита транзиентов.** Гейт на атаки ударных, чтобы ни де-шиммер,
ни экситер не смазывали щелчок.

**6. Мягкий клиппер перед лимитером.** Срезает самые острые пики
мягко, лимитеру остаётся меньше работы — меньше пампинга.

**7. Моно-бас ниже ~120 Гц.** Сейчас ширина добавляется только выше
2.5 кГц, но фазовые проблемы, уже пришедшие из Suno, в низе остаются.
Принудительное моно в самом низу — стандартная практика для клуба и
винила.

**8. Потолок по формату.** Переключатель «lossless −1.0 / стриминг −1.5
dBTP».

**9. Прослушка «только добавленное».** Третья кнопка рядом с «до/после»:
слышно только то, что Airband досинтезировал. Если там проступает
шиммер — значит, де-шиммер недоработал.

**10. Диапазон громкости (LRA) в показателях** — сколько динамики осталось
после обработки. Описан в EBU Tech 3342, есть в libebur128.

### P2 — паритет по оставшимся функциям (браузер)

**11. Подгонка под референс** — отношение сглаженных спектров,
ограничение ±6 дБ, как в Python.

**12. Альбомный режим** — общий сдвиг громкости на весь пакет.

**13. FIR-кроссоверы** с линейной фазой — нужны в первую очередь для
де-шиммера (разделение на 4.5 кГц), для экситера — по желанию.

### P3 — тяжёлые опции (только Python, отдельными модулями)

**14. Apollo** — нейросетевое восстановление MP3 как альтернатива
экситеру для 128 kbps исходников. Отдельный необязательный модуль со
своей лицензией CC BY-SA, не внутри MIT-кода. Перед коммерческим
использованием — проверить условия весов и датасетов.

**15. Стемы (Demucs)** — разделить трек на вокал/барабаны/бас/прочее и
восстанавливать верх по-разному: на вокале бережно, на тарелках
активнее. Так делают Shimmer и ai-mastering.

**16. AudioSR** — как экспериментальный режим для тех, у кого есть
видеокарта; сначала проверить на реальных треках из Suno.

## Что делать первым

Предлагаю идти так: **1 → 2 → 4**. Сначала честный true peak (это баг,
он может давать клиппинг на стримингах прямо сейчас), потом слежение за
огибающей (главный слышимый разрыв с Python), потом де-шиммер перед
экситером (главное улучшение по смыслу, касается обеих версий).
Остальное — по желанию и по очереди.

Чего я не проверяла сама: качество де-шиммера deshimmer и Apollo на
реальных треках Suno — это нужно слушать, а не мерить на синтетике.
